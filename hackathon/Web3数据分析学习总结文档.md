## 一、学习目标

学习 Web3 数据分析，不只是学会查数据或画图，而是要能够从链上数据中发现规律，并把这些规律转化成项目判断、产品建议或投资研究结论。

学完这一部分，你应该能够掌握：

- Web3 数据的来源和基本结构。
- 区块、交易、地址、智能合约、事件日志等核心概念。
- 如何理解链上数据和传统互联网数据的区别。
- 如何使用 Dune、The Graph、Hemera、ZAN 等工具进行数据分析。
- 如何设计常见 Web3 指标，例如活跃地址数、交易数、Gas 费用、Token 转账量、留存率等。
- 如何完成一个适合 Hackathon 或项目展示的数据分析报告。

## 三、什么是 Web3 数据分析

Web3 数据分析是指通过区块链上的公开数据，以及部分链下数据，分析用户行为、协议表现、资产流动、市场趋势和项目健康度。

传统互联网数据分析通常分析的是：

- 用户注册
- 点击行为
- 页面访问
- 订单数据
- 支付数据
- 留存和转化

Web3 数据分析更关注：

- 钱包地址行为
- 链上交易记录
- 智能合约交互
- Token 转账
- NFT 铸造和交易
- DeFi 流动性
- Gas 消耗
- 跨链行为
- DAO 治理行为

Web3 数据的特点：

- 数据公开透明，大量链上数据可以被任何人查询。
- 数据不可随意篡改，交易一旦确认就会永久保留。
- 用户身份通常是钱包地址，而不是真实姓名。
- 一个用户可能拥有多个钱包地址。
- 一个地址也可能不是人，而是合约、交易所、机器人或团队地址。
- 数据虽然公开，但理解和解释难度较高。

## 四、Web3 数据分析常见问题

学习 Web3 数据分析时，可以围绕这些问题展开：

- 某个协议每天有多少活跃用户？
- 某个合约被调用了多少次？
- 哪些钱包地址最活跃？
- 某个 Token 的转账量是否增长？
- NFT 项目的铸造人数和二级交易情况如何？
- 某次活动是否带来了真实用户增长？
- 用户是一次性参与，还是持续返回？
- 项目是否存在机器人刷量或异常交易？
- 某个地址是否可能是大户、机器人、交易所或合约地址？

好的数据分析不是“查出一堆数字”，而是回答一个具体问题。

## 五、核心链上数据概念

### 1. 区块

区块是区块链中存储交易的基本单位。多个交易会被打包进一个区块，区块按照时间顺序连接起来。

常见字段包括：

- 区块高度
- 区块时间
- 区块哈希
- 父区块哈希
- 验证者或矿工
- Gas 使用量
- Gas 上限

在数据分析中，区块常用于时间维度分析，例如按天、按小时统计交易数量。

### 2. 地址

地址是 Web3 世界中的基本身份单位。

地址主要分为两类：

- 外部账户地址：由私钥控制，通常是用户钱包。
- 合约账户地址：由智能合约代码控制。

需要注意：

```text
一个钱包地址不一定等于一个真实用户。
一个真实用户也可能拥有多个钱包地址。
```

所以在分析“用户数”时，很多时候只能用“活跃地址数”作为近似指标。

### 3. 交易

交易是链上状态变化的记录。用户转账、调用智能合约、铸造 NFT、兑换 Token，都会形成交易。

常见字段包括：

- 交易哈希
- 区块高度
- 交易时间
- 发送方地址
- 接收方地址
- 转账金额
- Gas 价格
- Gas 使用量
- 输入数据
- 交易状态

交易数据可以用于分析：

- 活跃度
- 用户行为
- 合约调用情况
- 手续费成本
- 资金流向

### 4. 智能合约

智能合约是部署在区块链上的程序。Web3 应用大多依赖智能合约运行。

例如：

- Token 合约
- NFT 合约
- 去中心化交易所合约
- 借贷协议合约
- DAO 治理合约

分析智能合约时，常见问题包括：

- 合约被多少地址调用？
- 哪些方法被调用最多？
- 合约每天产生多少交易？
- 合约消耗多少 Gas？
- 是否存在异常调用？

### 5. 事件日志

智能合约在执行过程中可以释放事件，事件会被记录为日志。

事件日志非常适合数据分析，因为它比原始交易输入更结构化。

例如，ERC-20 Token 转账通常会产生 `Transfer` 事件，其中包含：

- 发送方
- 接收方
- 转账数量

事件日志常用于分析：

- Token 转账
- NFT 铸造
- NFT 转移
- Swap 交易
- 流动性添加和移除
- 质押和解质押
- DAO 投票

## 六、数据分析基础知识

### 1. 数据分析基本流程

一个完整的数据分析流程通常包括：

1. 明确分析问题
2. 找到数据来源
3. 理解字段含义
4. 清洗和转换数据
5. 设计分析指标
6. 进行统计和可视化
7. 总结发现
8. 提出建议

初学者最容易犯的错误是：还没想清楚问题，就直接开始查数据。

### 2. 维度与指标

维度是用来分组和切分数据的角度。

常见维度：

- 时间
- 链
- 协议
- Token
- 合约
- 钱包地址
- 用户类型

指标是用来衡量结果的数值。

常见指标：

- 活跃地址数
- 交易数量
- 转账金额
- Gas 费用
- Token 持有人数量
- 留存率
- 增长率

例如：

```text
按天统计活跃地址数
按合约统计交易数量
按 Token 统计转账金额
按用户分组统计留存率
```

### 3. 常用统计概念

入门阶段需要掌握：

- 总数
- 平均值
- 中位数
- 占比
- 增长率
- 环比
- 同比
- 分布
- 异常值
- 相关性
- 留存
- Cohort 分组

一开始不需要急着学很复杂的机器学习。大多数项目分析，核心还是清晰的问题、准确的指标和可靠的解释。

### 4. 数据清洗

链上数据虽然结构化，但不代表可以直接使用。

常见清洗工作包括：

- 过滤失败交易
- 处理 Token 小数位
- 把时间戳转换成日期
- 区分钱包地址和合约地址
- 去重
- 排除明显机器人行为
- 排除交易所地址或桥地址
- 标准化字段名称

例如，很多 Token 原始数量不是直接的人类可读金额，而是需要除以 `10 ** decimals`。

## 七、SQL 在 Web3 数据分析中的作用

SQL 是 Web3 数据分析最重要的基础技能之一，尤其是在 Dune 这类平台中。

必须掌握：

- `SELECT`
- `FROM`
- `WHERE`
- `GROUP BY`
- `ORDER BY`
- `JOIN`
- `HAVING`
- `WITH`
- 窗口函数

示例：按天统计交易数。

```sql
SELECT
  DATE_TRUNC('day', block_time) AS day,
  COUNT(*) AS tx_count
FROM ethereum.transactions
WHERE success = true
GROUP BY 1
ORDER BY 1;
```

示例：按天统计活跃地址数。

```sql
WITH addresses AS (
  SELECT block_time, "from" AS address
  FROM ethereum.transactions
  WHERE success = true

  UNION ALL

  SELECT block_time, "to" AS address
  FROM ethereum.transactions
  WHERE success = true
)
SELECT
  DATE_TRUNC('day', block_time) AS day,
  COUNT(DISTINCT address) AS active_addresses
FROM addresses
WHERE address IS NOT NULL
GROUP BY 1
ORDER BY 1;
```

不同平台的数据表名称可能不同，所以写 SQL 前要先查看数据目录和字段说明。

## 八、Dune Analytics

### 1. Dune 是什么

Dune 是一个常用的 Web3 数据分析平台。它提供链上数据表、SQL 查询、可视化图表和公开 Dashboard。

Dune 适合：

- 快速查询链上数据
- 创建分析图表
- 搭建项目 Dashboard
- 学习别人写的 SQL
- 做 Hackathon 项目展示

### 2. Dune 数据类型

Dune 中常见的数据包括：

- 原始链上数据
- 解码后的合约数据
- Token 转账数据
- NFT 数据
- 协议整理后的数据模型
- 社区贡献的数据模型

原始数据灵活，但处理难度更高。整理后的数据更适合初学者。

### 3. Dune 分析流程

推荐流程：

1. 搜索链、协议或合约。
2. 查看可用数据表。
3. 查询少量样本数据。
4. 明确要计算的指标。
5. 使用 SQL 聚合数据。
6. 创建图表。
7. 组合成 Dashboard。
8. 为图表写简短解释。

### 4. 适合初学者的 Dune 主题

- 每日交易数
- 每日活跃地址数
- Token 转账趋势
- Top 合约调用排行
- Top 钱包地址排行
- Gas 费用趋势
- 新用户和老用户对比
- NFT 铸造趋势
- DeFi 交易量趋势

### 5. 使用 Dune 的注意事项

- 查询前先明确问题。
- 探索数据时使用 `LIMIT`。
- 注意交易是否成功。
- Token 数量要处理小数位。
- 地址标签只能辅助判断，不能完全依赖。
- Dashboard 要写清楚口径。
- 不要用不完整的数据做过度结论。

## 九、ZAN 平台

ZAN 是 Web3 基础设施和 API 服务平台。它更偏向开发和数据服务，不只是分析工具。

ZAN 可能用于：

- 获取区块链 RPC 服务
- 查询交易信息
- 查询地址信息
- 读取智能合约状态
- 监听合约事件
- 把链上数据接入应用后端

在数据分析项目中，ZAN 可以帮助你获取原始数据或接口数据，再结合 Python、SQL 或前端图表进行展示。

使用 API 时要注意：

- API Key 不要公开
- 注意请求频率限制
- 对重复请求做缓存
- 检查返回数据是否完整
- 处理异常和失败请求
- 记录数据获取时间

## 十、Ethereum 链上数据分析

Ethereum 是 Web3 数据分析最重要的学习对象之一，因为它拥有丰富的智能合约、Token、NFT 和 DeFi 数据。

### 1. Ethereum 常见数据表

在不同数据平台中，Ethereum 数据一般包括：

- 区块表
- 交易表
- 内部调用表
- 日志表
- Token 转账表
- NFT 转账表
- 合约创建表
- 解码事件表

### 2. Ethereum 常见指标

| 指标 | 含义 | 作用 |
| --- | --- | --- |
| 每日交易数 | 每天发生多少交易 | 衡量链上活跃度 |
| 活跃地址数 | 参与交易的独立地址数 | 近似衡量用户规模 |
| 新地址数 | 首次出现的地址数量 | 衡量增长 |
| Gas 使用量 | 消耗的计算资源 | 衡量网络使用压力 |
| Gas 费用 | 用户支付的手续费 | 衡量使用成本 |
| Token 转账量 | Token 流动规模 | 衡量资产活动 |
| 持有人数量 | 持有 Token 的地址数 | 衡量分布情况 |
| 合约调用数 | 合约被交互次数 | 衡量应用使用情况 |

### 3. 新用户与老用户

在 Web3 中，通常用地址来近似表示用户。

- 新地址：第一次出现或第一次与项目交互的地址。
- 老地址：之前已经出现过，并在当前周期再次活跃的地址。

这个分析适合判断：

- 活动是否带来新用户
- 用户是否持续回来
- 增长是否健康

### 4. 留存分析

留存分析用来判断用户是否在首次参与后继续使用。

例如：

```text
第一周首次使用的地址
第二周还有多少回来
第三周还有多少回来
第四周还有多少回来
```

留存分析可以用于：

- 判断产品粘性
- 评估活动质量
- 判断社区是否健康
- 分析用户长期价值

### 5. Gas 分析

Gas 分析可以回答：

- 用户什么时候付费最高？
- 哪些合约最消耗 Gas？
- 哪些操作成本最高？
- 合约升级后是否降低了成本？

如果你的项目声称“更省 Gas”或“更高效”，Gas 数据就是很重要的证明。

## 十一、Hemera

Hemera 的重点可以理解为链上数据索引和抽象。

原始链上数据虽然公开，但直接使用效率不高。索引服务会把原始数据整理成更适合查询和分析的数据结构。

索引的作用包括：

- 提高查询速度
- 建立结构化数据模型
- 支持地址视角分析
- 支持合约视角分析
- 支持跨链分析
- 支持项目级数据集

Hemera 这类平台适合分析：

- 钱包画像
- 跨链行为
- 协议交互历史
- 用户路径
- 应用增长
- 合约活跃度

核心学习点不是只会使用某个平台，而是理解：Web3 数据分析离不开索引。

## 十二、The Graph

The Graph 是一个用于索引和查询区块链数据的协议。开发者可以创建 Subgraph，把智能合约事件整理成可查询的数据实体。

### 1. Subgraph 是什么

Subgraph 可以理解为某个链上应用的数据模型。

它通常包括：

- 配置文件
- 数据结构定义
- 事件处理逻辑
- 数据源
- 映射关系

### 2. GraphQL 查询

The Graph 通常使用 GraphQL 查询数据。

示例：

```graphql
{
  transfers(first: 10, orderBy: timestamp, orderDirection: desc) {
    id
    from
    to
    value
    timestamp
  }
}
```

### 3. The Graph 适合什么场景

The Graph 适合：

- 为应用提供链上数据 API
- 查询协议级结构化数据
- 支持前端应用展示
- 分析 Swap、Pool、Position、Vote 等复杂业务对象

Dune 更适合做 SQL 分析和 Dashboard；The Graph 更适合给应用提供结构化数据接口。

## 十四、Dashboard 设计方法

一个好的 Dashboard 不应该只是堆图，而应该讲清楚一个故事。

推荐结构：

1. 顶部展示关键指标。
2. 展示核心趋势。
3. 按维度拆分数据。
4. 展示用户行为。
5. 展示异常或风险。
6. 写出结论和建议。

Hackathon 项目中，Dashboard 不需要特别复杂，但要清晰。

建议：

- 3 到 5 个关键指标
- 3 到 6 张图表
- 每张图配一句解释
- 明确和项目价值的关系

## 十六、项目示例：协议增长分析

### 1. 分析问题

某个协议是否在健康增长？

### 2. 关键指标

- 每日活跃地址数
- 每日交易数
- 新增地址数
- 回访地址数
- 留存率
- Token 交易量
- Gas 成本
- 合约调用分布

### 3. 健康增长的表现

通常包括：

- 活跃地址持续增长
- 回访用户增加
- 活动不是由少数地址刷出来的
- 交易成功率稳定
- 用户行为和核心产品功能相关

### 4. 不健康增长的表现

可能包括：

- 只有一天突然暴涨
- 活动集中在少数钱包地址
- 失败交易很多
- 大量重复机械交易

## 二十、常见错误

- 把钱包地址直接等同于真实用户。
- 忘记过滤失败交易。
- 忽略 Token 小数位。
- 只看总交易量，不看用户数。
- 用一天的数据波动做长期结论。
- Dashboard 有图但没有解释。
- 把相关性当成因果关系。
- 忽略机器人、交易所、桥和合约地址。
- 复制别人的 SQL 但不理解字段含义。
